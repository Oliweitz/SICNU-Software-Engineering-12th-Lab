## 0. 权威源与变更流程

**`docs/init.sql` 是表结构的唯一权威源。**

| 信息 | 权威源 | 其他位置的性质 |
|---|---|---|
| 表与字段 | `docs/init.sql` | 技术方案 §5 为**摘要**——允许不完整,**不允许矛盾** |
| 表归属权责 | 技术方案 §5.1 | 每张表有且仅有一个属主模块 |
| 枚举 / 字典型列的**取值清单** | **`sys_dict_item` 表**(数据字典,见 §12) | 列 `COMMENT` 只写字典编码,**不再罗列取值**;Java enum / 前端下拉必须与之逐一对应 |

**改表结构必须按此顺序**,不可颠倒:

1. 改 `docs/init.sql`
2. 若涉及字典取值增删 → 同步 `sys_dict_item` 的种子数据(新增一个字典类型**无需改表结构**,只加数据行)
3. 同步 `docs/技术方案.md` 第 5 节摘要(若涉及模块归属,同步 §5.1;若新增字典,同步 §5.1 与 §7 字典接口)
4. 更新本地库(全新环境重跑;已有数据的环境用增量脚本,见 §10)
5. 更新对应 Entity 类
6. 提交信息注明(如 `build(db): trial 表补 video_path 与自评量表字段`)

## 1. 数据项命名规范

### 1.1 表名

| 规则 | 说明 | 正例 | 反例 |
|---|---|---|---|
| 全小写 + 下划线分词 | 不用驼峰、不用大写 | `question_bank` | `QuestionBank`、`questionBank` |
| **单数** | 表是实体集合,用单数命名 | `task` | `tasks` |
| 系统表加 `sys_` 前缀 | 权限、字典与基础设施类表 | `sys_user`、`sys_dict_item` | `user`、`dict_item` |
| 关系表用 `_` 连接两实体 | **主体在前**,从属在后 | `clazz_student` | `student_clazz` |
| 不用拼音、不用缩写 | 除非是约定俗成缩写 | `certificate` | `zhengshu`、`cert` |
| **避开 MySQL 保留字** | 自检方法见 §9 | — | `order`、`group`、`key` |

> 本项目表名已全部通过保留字自检:`resource` / `task` / `trial` / `review` 等均为**非保留关键字**,可直接使用。

### 1.2 列名(数据项)

| 规则 | 正例 | 反例 |
|---|---|---|
| 全小写 + 下划线分词 | `real_name` | `realName`、`RealName` |
| 主键统一命名为 `id` | `id` | `user_id`(作主键时)、`pk` |
| 外键 `<实体>_id` | `clazz_id`、`teacher_id`、`task_id` | `clazzId`、`tid` |
| 布尔**禁止 `is_` 开头** | `deleted`、`enabled` | `isDeleted`、`is_deleted` |
| 时间列 `_at` 结尾 | `created_at`、`issued_at` | `createTime`、`issue_date` |
| 枚举列不加后缀 | `status`、`mode`、`type` | `status_code`、`type_flag` |
| JSON 列 `_json` 结尾 | `rubric_json`、`stage_times_json` | `rubric`、`rubric_data` |
| 数量/时长列语义明确 | `student_count`、`duration_minutes` | `num`、`dur` |

> **驼峰映射依据**:`application.yml` 中 `map-underscore-to-camel-case: true`,下划线列名自动映射到 Java 驼峰属性——`real_name` ↔ `realName`。命名规范与框架配置是配套的,不可单方面更改。

### 1.3 索引与约束命名

| 类型 | 前缀 | 格式 | 示例 |
|---|---|---|---|
| 主键 | — | `PRIMARY KEY (id)` | — |
| 唯一索引 | `uk_` | `uk_<列名>` 或 `uk_<列1>_<列2>` | `uk_username`、`uk_clazz_student` |
| 普通索引 | `idx_` | `idx_<列名>` 或 `idx_<列1>_<列2>` | `idx_teacher`、`idx_task_student` |
| 外键 | **不建**,见 §5.3 | — | — |

> 索引名必须能直接读出它建在哪几列上。`idx_a` 这类无信息量命名禁止使用。

## 2. 数据类型规范

**核心原则:MySQL 类型与 Java 类型一一对应,不留隐式转换。**

| 用途 | MySQL 类型 | Java 类型 | 说明 |
|---|---|---|---|
| 主键 / 外键 | `BIGINT` | `Long` | **不用 `BIGINT UNSIGNED`**——它超出 `Long` 表达范围,JDBC 读取需转 `BigInteger`,是常见踩坑点 |
| 短字符串 | `VARCHAR(n)` | `String` | n 取值见 §2.1 |
| 枚举码 | `VARCHAR(20)` | `enum` | 不用 MySQL `ENUM`(增删取值需 DDL);不用 `TINYINT`(可读性差) |
| 分数 | `DECIMAL(5,1)` | `BigDecimal` | 范围 0.0~9999.9;本项目分数为 0.0~100.0 |
| 布尔 | `TINYINT` | `Integer` | 0 / 1(MyBatis-Plus `@TableLogic` 要求) |
| 时间 | `DATETIME` | `LocalDateTime` | **不用 `TIMESTAMP`**——有 2038 上限,且会隐式按时区转换 |
| 结构化数据 | `JSON` | `String` | MySQL 8 原生类型,**写入时即校验格式**,见 §2.3 |
| 长文本 | `TEXT` / `MEDIUMTEXT` | `String` | 见 §2.2 |

### 2.1 `VARCHAR` 长度取值表

| 语义 | 长度 |
|---|---|
| **字典码**——所有纳入数据字典的列(`role` / `mode` / `status` / `type` / `stage` / `subject` / `course` / `major` / `grade` / `textbook_version` / `certificate.type`) | `VARCHAR(20)` |
| 字典类型编码 `sys_dict_type.dict_type` | `VARCHAR(50)` |
| 字典标签 `sys_dict_item.item_label`、姓名、字典名称 | `VARCHAR(50)` |
| 任务标题、班级名、资源标题 | `VARCHAR(100)` |
| 密码哈希(BCrypt 定长 60 字符) | `VARCHAR(100)` |
| 文件路径 | `VARCHAR(255)` |

> 长度按业务上限取值,**不要一律 `VARCHAR(255)`**——过长的字符列会拖慢临时表与排序操作。

> **字典型列一律 `VARCHAR(20)`,没有例外。** 表中"专业 / 年级 / 学科 / 教材版本 / 证书类型"五项原本按中文取值定为
> `VARCHAR(50)`,纳入数据字典(§12)后列内存的是**字典码**(`CHINESE_EDU` / `2023` / `MATH` / `PEP` / `EXPRESSION`),
> 故统一下调为 `VARCHAR(20)`;中文标签移到 `sys_dict_item.item_label`(`VARCHAR(50)`)。
> 这同时消除了本节旧版与 §2 主表之间的一处自相矛盾——`certificate.type` 既是枚举码又是 `VARCHAR(50)`。

### 2.2 `TEXT` 类型选择

| 类型 | 上限 | 本项目用法 |
|---|---|---|
| `TEXT` | 64 KB | 题目内容、答题要点、教师点评、资源正文等普通长文本 |
| `MEDIUMTEXT` | 16 MB | 试讲稿(含大量 `[环节]` / `[板书]` 标注,篇幅不可控) |

### 2.3 `JSON` 类型使用规约

- **所有存 JSON 的列一律用 `JSON` 类型,不用 `TEXT`**
- 收益:写入时即校验格式(写坏的 JSON **当场报错**,而非评测时读出才炸)
- Java 侧仍以 `String` 映射,MyBatis-Plus 默认即可工作,**无需额外 TypeHandler**
- 注意:MySQL 会对 JSON 做规范化(重排键、去空白),**原文不逐字节保留**——读取方必须解析而非做字符串比较
- JSON 列**不可有 `DEFAULT` 值**,也**不可直接建索引**;若将来需按 JSON 内字段检索,用「生成列 + 索引」:

  ```sql
  ALTER TABLE evaluation_report
    ADD COLUMN content_score DECIMAL(5,1)
      GENERATED ALWAYS AS (JSON_EXTRACT(dimension_scores_json, '$.content.score')) STORED,
    ADD KEY idx_content_score (content_score);
  ```
- JSON 列的 `NULL` 表示"该数据不存在"(如未启用音视频评测),**不要写入字符串 `"null"`**

## 3. 必备列(审计列)

| 列 | 类型 | 说明 | 豁免 |
|---|---|---|---|
| `id` | `BIGINT NOT NULL AUTO_INCREMENT` | 主键,必须声明 `PRIMARY KEY` | 无 |
| `created_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` | 创建 / 提交时间 | 无 |
| `updated_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | 更新时间,由数据库自动维护 | 见白名单 |
| `deleted` | `TINYINT NOT NULL DEFAULT 0` | 逻辑删除标志,0 正常 / 1 已删除 | 见白名单 |

### 豁免白名单(全项目仅此两处)

| 表 | 豁免列 | 理由 |
|---|---|---|
| `clazz_student` | `updated_at`、`deleted` | **纯关系表**:关系解除即物理删除,无需软删;关系本身无"修改"语义 |
| `certificate` | `updated_at` | **只增不改的业务表**:证书一经颁发不可修改,时间语义由业务列 `issued_at` 承担 |

> 新增表若需豁免,必须在本节登记理由;未登记即评审不通过。

## 4. 索引规范

### 4.1 建索引的强制要求

- 主键必须显式声明 `PRIMARY KEY (id)`
- **所有外键列必须建索引**(即使不建物理外键)——关联查询必然用到
- 凡出现在 `WHERE` / `JOIN ON` / `ORDER BY` 的列,必须有索引覆盖
- 组合索引遵循**最左前缀**原则:`idx_task_student (task_id, student_id)` 可同时服务「只查 `task_id`」与「查 `task_id` + `student_id`」两种查询,**因此不得再单建 `idx_task_id`**(冗余索引徒增写入开销)

> 字典表同理:`sys_dict_item` 的 `uk_type_value (dict_type, item_value)` 最左前缀已覆盖「按 `dict_type` 列出全部字典项」,
> **不得再单建 `idx_dict_type`**。字典列(`subject` / `stage` / `status` 等)的基数极低,
> 且真实查询几乎总是"按班级 / 按学生查,再展示标签",**不单独建索引**——详见 §12.4 第 2 条。

### 4.2 唯一索引的使用边界

唯一索引只用于**业务上要求全局唯一**的列:

| 表.列 | 唯一索引 | 业务含义 |
|---|---|---|
| `sys_user.username` | `uk_username` | 学号 / 工号,全局唯一 |
| `clazz_student.(clazz_id, student_id)` | `uk_clazz_student` | 同一学生不可重复入同一班级 |
| `evaluation_report.trial_id` | `uk_trial` | 一次试讲对应且仅对应一份报告 |

### 4.3 已知限制:唯一索引不感知逻辑删除

逻辑删除后物理记录仍在,唯一索引依然占用原值。例如 `sys_user` 中的学生被逻辑删除后,其 `username` **无法被重新注册**。

**本项目接受该限制,不做变通。** 理由:`username` 承载的是学号 / 工号,教育业务中**学号天然不复用**(学生毕业后学号不再分配给他人),该限制与业务语义一致。

> 若将来出现确需回收的唯一值,改用「未删除置 `1`、已删除置 `NULL`」的方案(`NULL` 不参与唯一性比较),并同步调整 MyBatis-Plus 的 `logic-delete-value` 配置。

### 4.4 索引注释

MySQL 8 **不支持对索引写 `COMMENT`**。因此**每个索引必须在上一行用 `--` 注释说明它服务于哪个查询**,便于评审与后续维护:

```sql
    -- 服务查询：按班级列任务 / 学生查看本班任务
    KEY idx_clazz (clazz_id),
```

## 5. 约束规范

### 5.1 非空与默认值

- 业务上必然有值的列一律 `NOT NULL`
- **必填业务列不给 `DEFAULT`**:如 `username` / `password` / `real_name` / `role`。
  漏赋值时数据库直接报错是**期望行为**——禁止用 `DEFAULT ''` 掩盖必填项,那会让空值静默入库
- **状态列、计数列给合理 `DEFAULT`**:如 `status DEFAULT 'PUBLISHED'`、`deleted DEFAULT 0`,取值须在该列 `COMMENT` 的枚举清单内
- 时间列与逻辑删除列的 `DEFAULT` 由 §3 统一给定,无需各表重复约定

### 5.2 唯一约束

- 仅用于 §4.2 登记的列
- 命名必须使用 `uk_` 前缀

### 5.3 外键:**不建物理外键**

全项目不使用 `FOREIGN KEY` 约束,引用完整性由 Service 层保证。

| 理由 | 说明 |
|---|---|
| 与逻辑删除冲突 | 父行逻辑删除后物理记录仍在,外键约束依然生效,删除子行会被阻塞 |
| 与架构演进冲突 | 技术方案 §3.1 有微服务拆分蓝图,拆库后物理外键无法维持 |
| 应用层可控 | Service 层校验 + 事务,便于批量操作与后续分库分表 |

**代价与对策**:不建外键 ⇒ 外键列的索引与校验责任转移到应用层。
- Service 层插入子记录前,**必须校验父实体存在**(如提交试讲前校验 `task` 存在且状态为 `PUBLISHED`)
- 表归属与跨模块读写规则见技术方案 §5.1

## 6. 字符集、排序规则与存储引擎

```sql
CREATE DATABASE ai_trial_platform
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

CREATE TABLE xxx (...) ENGINE = InnoDB COMMENT ='...';
```

| 项 | 取值 | 理由 |
|---|---|---|
| 字符集 | `utf8mb4` | 中文、生僻字、emoji 均需 4 字节;`utf8`(3 字节)会截断 |
| 排序规则 | `utf8mb4_0900_ai_ci` | MySQL 8 默认规则(Unicode 9.0),**性能与中文排序准确性均优于**旧的 `utf8mb4_unicode_ci` |
| 存储引擎 | `InnoDB` | 支持事务与行级锁;`MyISAM` 无事务,**禁止使用** |

> 字符集与排序规则在**库级**指定,表与列继承即可,不重复声明(减少噪音,避免库/表/列三者不一致)。

## 7. 注释规范

- **每张表必须有 `COMMENT`**,一句话说明业务含义
- **每个列必须有 `COMMENT`**
- **枚举 / 字典型列的 `COMMENT` 只写字典编码,不罗列取值**,格式:`'状态（字典 trial_status，值为字典码）'`
  > 取值权威源唯一收敛在 `sys_dict_item`(§12)——`COMMENT` 与字典两处罗列必然漂移,
  > 且列注释里的取值清单**前端取不到**。这里只留"去哪本字典查"的线索,不复制清单本身。
- 迭代后置的列,在 `COMMENT` 中注明迭代号:`'（可选，迭代 4）'`
- 可空列在 `COMMENT` 中说明何时为空(如 `'（失败回退时为 NULL）'`)

## 8. 逻辑删除规范

- 统一使用 `deleted TINYINT NOT NULL DEFAULT 0`,**0 正常 / 1 已删除**
- 与 `application.yml` 中 MyBatis-Plus 配置严格对应:

  ```yaml
  mybatis-plus:
    global-config:
      db-config:
        logic-delete-field: deleted
        logic-delete-value: 1
        logic-not-delete-value: 0
  ```

- **MyBatis-Plus 会自动为 `BaseMapper` 的查询追加 `WHERE deleted = 0`;手写 XML 的查询必须显式带上该条件**,否则会查出已删除数据
- 表若定义 `deleted`,Entity 对应字段必须加 `@TableLogic` 注解

## 9. 保留字自检

表名 / 列名投入使用前,用以下语句确认:

```sql
SELECT WORD, RESERVED
FROM INFORMATION_SCHEMA.KEYWORDS
WHERE WORD IN ('TASK','TRIAL','RESOURCE','REVIEW','STATUS','TYPE','MODE','COMMENT');
```

- `RESERVED = 1` → **不能**直接作标识符,必须改名
- `RESERVED = 0` → 可安全使用(属非保留关键字)
- 查询无结果的词 → 不是关键字,可安全使用

**本项目实测结论**(MySQL 8.0.45):`GROUP` / `KEY` / `ORDER` 为保留字,已避开;
`RESOURCE` / `STATUS` / `TYPE` / `MODE` / `COMMENT` 等为非保留关键字,可安全使用。

## 10. 数据库的建立与演进

按用途拆成两类脚本,职责分离:

| 脚本 | 用途 | 是否含 `DROP` |
|---|---|---|
| `docs/init.sql` | **全新环境初始化**(答辩演示、新成员 clone、重装环境) | 含 `DROP DATABASE IF EXISTS` |
| `docs/migration/V<n>__<描述>.sql` | **已有数据环境的增量变更** | 不含,只写 `ALTER TABLE` / `CREATE TABLE` |

**规则**:迭代 1 起的每一次表结构变更,都要

1. 写一份 migration 增量脚本(如 `V3__iter3_review_voice.sql`;编号顺延,已应用的老脚本**不再修改**)
2. 同步把该变更**合并进 `init.sql`**,保证新库仍能一次建好
3. 提交信息注明

> 只维护 `init.sql` 会导致每次改表都要清库重来;**只维护 migration** 则新成员无法一次建库。两者必须同步。

**已归档的脚本记录**(回答"这个变更当初是怎么进库的"):

| 脚本 | 内容 | 现状 |
|---|---|---|
| `V1__db_spec_gaps.sql` | `certificate.idx_task` 索引;`task` / `trial` 列 `COMMENT` 补全取值范围与空值语义 | **内容已全部并入 `init.sql`,脚本已删除**。该变更另以**幂等**形式重现在 `V2` 第 1 节,故未跑过原 V1 的库跑一次 `V2` 即可收敛 |
| `V2__data_dict.sql` | 建 `sys_dict_type` / `sys_dict_item`;13 本字典的种子数据;字典型列中文取值 → 字典码;列宽与 `COMMENT` 收敛 | 当前最新;可重复执行 |

> **脚本可重复执行**是硬要求:执行到一半失败、或不确定有没有跑过时,能直接重跑而不报错。
> 判断索引是否存在用 `information_schema` + `PREPARE`(MySQL 不支持 `ADD INDEX IF NOT EXISTS`);
> 数据变更用 `WHERE` 限定原值,使其天然幂等。

## 11. 评审清单(建表 / 改表时逐项核对)

- [ ] 表名全小写单数、非保留字;关系表主体在前

## 12. 数据字典

### 12.1 为什么要有数据字典

迭代 0 的取值清单写在 10 张业务表的列 `COMMENT` 里,暴露出三个问题:

| 问题 | 具体表现 |
|---|---|
| **同一取值域在多表各写一份** | 学科在 `clazz.course` / `task.subject` / `question_bank.subject` / `resource.subject` **四处**重复登记,任何一处漏改就产生漂移;学段在 `task` / `question_bank` 两处重复 |
| **自由文本列约束不住** | `sys_user.major`、`sys_user.grade`、`task.textbook_version`、`certificate.type` 用 `VARCHAR(50)` 存中文,写什么都进得去——按专业 / 按教材版本统计的结果不可信 |
| **前端无接口可取** | 下拉选项只能在前端硬编码,枚举一改就要重新发版;而列 `COMMENT` 里的清单**根本读不到** |

数据字典把"**有哪些取值**"这件事从列注释收口到两张表:一条数据行即可维护,前端有接口可查,Service 层有依据可校验。

### 12.2 表结构

`sys_dict_type`(类型表:有哪些字典)+ `sys_dict_item`(明细表:每本字典有哪些取值)。

**为什么是通用两表,而不是每个字典建一张专表**

| 取舍 | 通用两表(本项目采用) | 每个字典一张专表 |
|---|---|---|
| 新增一个字典 | `INSERT` 一行数据,**零 DDL** | 建一张新表 + 改代码 + 写 migration |
| 表数量 | 2 | 13 个字典 ⇒ 13 张结构雷同的表 |
| 管理界面 | 一套 CRUD 通吃 | 每个字典各写一套 |
| 加字典级专属字段 | 需要时才扩列 | 天然可加 |
| 可读性 | 要 join 才知道"有哪些取值" | 表名即语义 |

> 本项目 13 个字典中没有一个需要专属字段,采通用两表;若将来某个字典确实长出专属属性
> (如"学科"要挂学段范围),再把它单独抽成专表,其余字典不受影响——这正是可演进的方向。

**为什么调用方用 `dict_type` 英文编码,而不是字典表的自增 id**

字典要能被 SQL、配置文件、前端直接读懂:`dict_type = 'subject'` 一眼知道查的是学科,
而 `dict_type_id = 4` 换一个库、换一次初始化顺序就变。故 `sys_dict_type` 用 `uk_dict_type (dict_type)` 作业务唯一键,
业务与代码一律引用编码。

### 12.3 取值权威源(§0 的展开)

| 场景 | 权威源 | 其他位置 |
|---|---|---|
| 表列上的枚举 / 字典型取值 | **`sys_dict_item`** | 列 `COMMENT` 只写字典编码 |
| **JSON 内部**的枚举键(报告里的维度 key `content` / `posture`、问题级别 `WARN`) | **Java 枚举**(`Dimension` / `IssueLevel`) | **不入字典** |
| 纯代码内契约(错误码 `ResultCode` 等) | Java 枚举 | 不入字典 |

> **JSON 内的枚举为什么不入字典**:字典表提供的是**行级**取值约束,而 JSON 列内部是自由结构,
> 数据库层面约束不到——收进字典只会制造"字典里有一份、JSON 里还可能是别的值"的假象。
> 这类取值由 Java 枚举在**写入前**校验,权威源是枚举本身(见技术方案 §6.3「维度 key 取值受控」)。
> **判定口径**:这个取值会不会成为一个独立列的取值?会 → 进字典;只在 JSON 对象内部出现 → 归 Java 枚举。

### 12.4 使用规约

1. **业务表存字典码,不存中文标签。** `task.subject` 存 `MATH` 而非 `数学`。
   - 与 §2「枚举码与 Java 一一对应」一致,全库枚举列风格统一(此前中文与码值混用)
   - 中文文案要改(如"幼教"→"学前教育")只改字典一行,**不动业务数据**
2. **常规查询不需要 join。** 业务列自带码值,列表 / 统计 / 排序 / 分组直接查;
   只有**渲染中文标签**时才需要字典。字典数据变化频率极低,应用层**一次性加载进本地缓存**
   (迭代 3 起可换 Redis),不存在逐行查字典的开销——这也解释了为什么"给课程建字典表"不会拖慢查询。
3. **写入前必须校验取值。** 本项目不建物理外键(§5.3),所以"这个码在不在这本字典里"由 Service 层校验,
   校验不过抛 `BizException`——与 §5.3「引用完整性由 Service 层保证」是同一套机制。
4. **停用与删除语义不同,不要混用。**
   - `enabled = 0` **停用**:该项不可再被选中,但**历史数据仍按标签正常展示**(如某版教材停用)
   - `deleted = 1` **逻辑删除**:整个字典项作废。§4.3 的已知限制同样适用——逻辑删除后
     `uk_type_value` 仍占用原值,同一个 `dict_type + item_value` **无法再重建**。
     **绝大多数场景应选"停用"而非"删除"。**
5. **字典项改标签是全量生效的;改码不是。** 若把码本身改掉(`MATH` → `MATHEMATICS`),
   必须同时 `UPDATE` 所有引用该码的列,并新建一个 migration 脚本(§10)——**禁止只改字典表就了事**。
6. **字典管理是写操作,归 `dict` 模块。** 其余模块只读(技术方案 §5.1 R-1:可跨模块读表,不可跨模块写表)。

### 12.6 字典表自身的规约

- 两表与其他业务表同等要求:`id` / `created_at` / `updated_at` / `deleted` 四列齐全,**无豁免**(§3 白名单不含字典表)

- 建表与改表同样走 §10 的双轨流程:`init.sql` 改结构,`docs/migration/` 补增量脚本
